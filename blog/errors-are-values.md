---
title: エラーは値である
date: 2015-01-12
by:
- Rob Pike
summary: Go でエラーを処理するためのイディオムとパターン。
---

Go プログラマーの間で、特に言語を学び始めたばかりの人たちの間でよく話題になるのが、エラーをどう処理するかということです。この話はしばしば、次のようなシーケンスが何度も出てくることへの不満として語られます。

```go
if err != nil {
	return err
}
```

実際に私たちは、見つけられるオープンソースプロジェクトをすべて調べたところ、このスニペットは1〜2ページに1回程度しか出現せず、一部の人が思っているよりも少ないことが分かりました。それでも、

```go
if err != nil
```

を常に書かなければならないという印象が根強く残っているなら、何かがおかしいはずで、その原因として Go 自体が疑われるのは明らかです。

これは不幸なことであり、誤解を招くものであり、簡単に修正できます。おそらく実際に起きていることは、Go を始めたばかりのプログラマーが「エラーはどう処理するのか？」と尋ね、このパターンを学んで、そこで止まってしまうということです。他の言語では、エラーを処理するために try-catch ブロックや類似の仕組みを使うことがあります。そのため、プログラマーは、以前の言語で try-catch を使っていた場面では、Go では単に `if` `err` `!=` `nil` と書けばいいのだと考えます。時間が経つにつれ、Go のコードにはそうしたスニペットが多く集まり、結果としてぎこちない印象になります。

この説明が当てはまるかどうかはともかく、こうした Go プログラマーがエラーについての根本的な点を見落としていることは明らかです。*エラーは値である。*

値はプログラムの対象にできます。そしてエラーは値であるため、エラーもプログラムの対象にできます。

もちろん、エラー値に関してよくある処理は nil かどうかを調べることですが、エラー値に対してできることは他にも数多くあり、そうした他の処理を活用することで、すべてのエラーを決まり文句の if 文で確認することから生じる多くの定型的なコードを排除し、プログラムをより良くできます。

`bufio` パッケージの [`Scanner`](/pkg/bufio/#Scanner) 型を使った簡単な例を見てみましょう。その [`Scan`](/pkg/bufio/#Scanner.Scan) メソッドは内部で I/O を実行するため、当然エラーが発生する可能性があります。しかし `Scan` メソッドはエラーを一切公開しません。代わりに真偽値を返し、スキャンの終わりに実行する別のメソッドで、エラーが発生したかどうかを報告します。呼び出し側のコードは次のようになります。

```go
scanner := bufio.NewScanner(input)
for scanner.Scan() {
	token := scanner.Text()
	// process token
}
if err := scanner.Err(); err != nil {
	// process the error
}
```

確かにエラーの nil チェックはありますが、それは一度だけ現れて実行されます。`Scan` メソッドは代わりに次のように定義することもできたでしょう。

```go
func (s *Scanner) Scan() (token []byte, error)
```

そして、呼び出し側のコード例は（トークンをどう取得するかによりますが）次のようになるかもしれません。

```go
scanner := bufio.NewScanner(input)
for {
	token, err := scanner.Scan()
	if err != nil {
		return err // or maybe break
	}
	// process token
}
```

これはそう大きく違うわけではありませんが、重要な違いが1つあります。このコードでは、呼び出し側はイテレーションのたびにエラーを確認しなければなりませんが、実際の `Scanner` API では、エラー処理は、トークンを反復処理するという API の核となる要素から抽象化されています。実際の API では、そのため呼び出し側のコードはより自然に感じられます。終わるまでループし、それからエラーについて考える、という具合です。エラー処理が制御フローを曇らせません。

もちろん、内部で起きているのは、`Scan` が I/O エラーに遭遇するとすぐにそれを記録し、`false` を返すということです。別のメソッド [`Err`](/pkg/bufio/#Scanner.Err) が、呼び出し側から求められたときにエラー値を報告します。これは些細なことですが、いたる所に

```go
if err != nil
```

を置くことや、呼び出し側に毎トークンごとにエラーを確認させることとは違います。これはエラー値によるプログラミングです。単純なプログラミングではありますが、それでもプログラミングです。

どのような設計であっても、プログラムがエラーをどう公開するかにかかわらず、それを確認することが重要だという点は強調しておく価値があります。ここでの議論は、エラーの確認を避ける方法についてではなく、言語を使って優雅にエラーを処理することについてです。

このエラーチェックの繰り返しというテーマが出てきたのは、私が2014年秋に東京で行われた GoCon に参加したときのことでした。Twitter で [`@jxck_`](https://twitter.com/jxck_) として知られる熱心な gopher が、エラーチェックについて同じようによく聞く不満を口にしました。彼のコードは概略すると次のようなものでした。

```go
_, err = fd.Write(p0[a:b])
if err != nil {
	return err
}
_, err = fd.Write(p1[c:d])
if err != nil {
	return err
}
_, err = fd.Write(p2[e:f])
if err != nil {
	return err
}
// and so on
```

これは非常に繰り返しが多いコードです。実際のコードはもっと長く、他にも処理があったため、ヘルパー関数を使って単純にリファクタリングするのは簡単ではありませんでしたが、この理想化された形では、エラー変数をクロージャで囲む関数リテラルが役立ちます。

```go
var err error
write := func(buf []byte) {
	if err != nil {
		return
	}
	_, err = w.Write(buf)
}
write(p0[a:b])
write(p1[c:d])
write(p2[e:f])
// and so on
if err != nil {
	return err
}
```

このパターンはうまく機能しますが、書き込みを行う関数ごとにクロージャが必要です。別のヘルパー関数にすると、`err` 変数を呼び出しをまたいで保持する必要があり、使いづらくなります（試してみてください）。

これは、上の `Scan` メソッドのアイデアを借用することで、よりきれいに、より汎用的で、再利用可能にできます。私はこの議論の中でこの手法について触れましたが、`@jxck_` にはそれをどう適用すればいいのか分かりませんでした。言語の壁にもいくらか苦しめられながら長く話し合った後、私は彼のラップトップを借りて、実際にコードを書いて見せてもいいか尋ねました。

私は `errWriter` というオブジェクトを、次のように定義しました。

```go
type errWriter struct {
	w   io.Writer
	err error
}
```

そして `write` というメソッドを1つ与えました。標準的な `Write` のシグネチャに従う必要はなく、その違いを強調するために一部小文字にしています。`write` メソッドは、内部の `Writer` の `Write` メソッドを呼び出し、後で参照するために最初のエラーを記録します。

```go
func (ew *errWriter) write(buf []byte) {
	if ew.err != nil {
		return
	}
	_, ew.err = ew.w.Write(buf)
}
```

エラーが発生すると、`write` メソッドはすぐに何もしなくなりますが、エラー値は保存されます。

`errWriter` 型とその `write` メソッドがあれば、上のコードは次のようにリファクタリングできます。

```go
ew := &errWriter{w: fd}
ew.write(p0[a:b])
ew.write(p1[c:d])
ew.write(p2[e:f])
// and so on
if ew.err != nil {
	return ew.err
}
```

これはクロージャを使った場合と比べてもよりきれいで、実際にどの書き込み処理が行われているかもページ上で見やすくなります。もう余計なものはありません。エラー値（とインターフェース）を使ったプログラミングによって、コードが良くなりました。

同じパッケージ内の他のコードも、このアイデアの上に成り立っている、あるいは `errWriter` を直接使っている可能性が高いでしょう。

また、`errWriter` ができてしまえば、特にもっと実践的な例では、さらに多くのことができます。バイト数を累積することもできますし、書き込みを1つのバッファにまとめて、それをアトミックに送信することもできます。他にもいろいろできます。

実際、このパターンは標準ライブラリの中でもよく見られます。[`archive/zip`](/pkg/archive/zip/) パッケージや [`net/http`](/pkg/net/http/) パッケージはこれを使っています。この議論にとってより重要なのは、[`bufio` パッケージの `Writer`](/pkg/bufio/) が実際に `errWriter` のアイデアを実装したものだということです。`bufio.Writer.Write` はエラーを返しますが、それは主に [`io.Writer`](/pkg/io/#Writer) インターフェースに準拠するためのものです。`bufio.Writer` の `Write` メソッドは、上の私たちの `errWriter.write` メソッドとまったく同じように振る舞い、`Flush` がエラーを報告します。そのため、私たちの例は次のように書けます。

```go
b := bufio.NewWriter(fd)
b.Write(p0[a:b])
b.Write(p1[c:d])
b.Write(p2[e:f])
// and so on
if b.Flush() != nil {
	return b.Flush()
}
```

少なくとも一部のアプリケーションにとって、このアプローチには大きな欠点が1つあります。エラーが発生するまでにどれだけの処理が完了していたかを知る方法がないことです。その情報が重要であれば、もっと細かい粒度のアプローチが必要です。しかし多くの場合、最後に「全部成功か、何もしていないか」を確認するだけで十分です。

ここでは、繰り返しの多いエラー処理コードを避けるための手法を1つだけ見てきました。`errWriter` や `bufio.Writer` の利用がエラー処理を単純化する唯一の方法ではなく、このアプローチがすべての状況に適しているわけでもないことを念頭に置いてください。しかし、ここでの重要な教訓は、エラーは値であり、それを処理するために Go 言語の力をすべて活用できるということです。

言語を活用して、エラー処理を単純化しましょう。

しかし忘れないでください。何をするにしても、常にエラーは確認してください！
